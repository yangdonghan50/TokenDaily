## 维护规则

1. 新功能、缺陷修复，或任何影响用户可见行为、数据口径、提醒、设置、系统集成、图标及安装包的改动，在开始编码时建立一个 `CHG-日期-序号` 条目。纯文档和不改变行为的机械整理仍记入 `docs/PROGRESS.md`；一旦影响共用契约，也须在这里登记。
2. 每条先写**统一目标行为和验收条件**，再分别维护 `Windows`、`macOS` 两行：状态、任务分支/提交、实际测试系统与结果。平台不同的原生实现可以不同，用户看到的数据含义和关键交互应一致。若某能力确实只适用于一端，另一端写“不适用”及对应体验或原因，不能留空。
3. 状态只用：`待做`、`开发中`、`待验证`、`已验证`、`阻塞`、`不适用`。`已验证` 要附日期、系统、提交 SHA 和实际执行的测试/安装态检查；代码共用、编译通过或另一端测过都不能代替本端验收。真实/演示数据及已知限制也要写清。
4. 跨平台改动先登记同一条目，再安排 Windows 和 Mac 两侧任务。两端开发时分别编辑本条目的平台行，不同时改写目标行为；如需改变目标行为，先同步更新验收条件。并行分支发生文档冲突时保留两端结果，逐项核对后合并。
5. 两端改动先合到同一个 `shared/<任务>` 集成分支，对同一集成代码在 Windows 和 Mac 分别验收；都达到约定条件，才标记 `同步完成` 并作为跨平台功能合入或发布。现有 Windows 功能是 Mac 的迁移清单，不因共用代码存在而视为同步完成。若一端尚未具备构建环境，新增跨平台功能保留在任务分支；确需单端先合入时，记录原因、另一端负责人及补齐目标，由用户明确决定该例外，不得写成“两端完成”。纯平台修复可在另一端明确“不适用”后按目标系统验收。
